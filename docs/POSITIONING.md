# Positioning — end-user reassurance channel

## Core Message (Commander's Intent)

**Hand it over. We've got it. Proof comes to us — not the reverse.**

If end users remember one thing about the portal + ticket emails, it's that
a real person owns their request and the system tells them what's happening
without them chasing. This is the emotional hire (Phase 1) made concrete.

## What that means per surface

| Surface | Rule |
|---|---|
| Created email | Name the ticket number, never sound like an inventory record; state Expected Resolution when it exists; promise a follow-up email on every move |
| Status email | Plain-language meaning, never raw status slugs (`in_progress`) — pending explicitly says who's waiting on whom |
| Empty states | Never silent ("No comments yet") — state the next signal with a timestamp ("you get an email the moment anything changes") |
| Submission flash | Name the deadline, not a vague "we'll review shortly" |
| Status badge | Raw label + one-line human gloss under it |

## Honesty guardrails (from intake: upsell badges honesty-scoped)

- Never promise a response time the system does not enforce. Only the
  computed Expected Resolution deadline is ever quoted.
- Gloss must stay truthful per status (`pending` = "we're waiting on
  something", not "we're on it").
- No invented social proof, no praise without a real count.
- "found this helpful" is a strict yes-tally — dismiss votes never count
  (Added Phase 7: helpful form is two real options, not a forced yes).
- "Most Read" is an exact statement of the ordering — never "Recommended".

## Not positioned

Internal agent channel keeps its functional voice — the reassurance copy is
for the end-user hire only.
